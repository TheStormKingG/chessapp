## 0. Why this feature and what it has to be

PRD §2.2 defines the North Star as Daily Active Learners, and states plainly:
**"Playing a game without reviewing it does not count."** §6.1 makes review the
third of four steps in the core loop and the source of the error log that step
four consumes. §8.6's preamble calls review "the highest-evidence activity in
the research".

Today every game in the app ends at a **disabled** control reading
"Review this game" with the caption "Coming next release."
(`src/play/PlayScreen.tsx:283–286`). That control is the most visible dead end
in the product, and nothing in the app currently writes an error log, so the
"fix" half of the loop has no input.

This document specifies the build that closes that loop. It takes the scope
decision as given (§2), states everything the build assumes, and records three
places where the PRD as written cannot be implemented literally (§9).

## 1. Measured facts the design is built on

Every number in this section was produced by running the **shipped engine
binary** over a **real 79-ply game**. Nothing here is recalled or estimated
unless it says so.

### 1.1 Method

- Engine: `public/engine/stockfish-19-lite-single.js` +
  `stockfish-19-lite-single.wasm`. Verified byte-identical (`cmp`) to
  `node_modules/stockfish/bin/` — the benchmark loaded the `node_modules` copy
  only because `public/` inherits `"type": "module"` from `package.json` and the
  engine file is CommonJS.
- Game: 79 plies (40 moves), generated by engine self-play at `Skill Level 1`,
  `go depth 4` — a blunder-rich game of the kind the app actually produces.
  80 reached positions plus the start position = **81 analysed positions**, which
  is the F-RV-1 workload ("a 40-move game").
- Settings: `Threads 1`, `Hash 16` unless stated, `ucinewgame` before the run,
  one warm-up position excluded from all timings.
- Host: Apple M1, macOS 25.6.0.
- Two harnesses: Node (`node:worker`-free, direct `ccall`) and **Chromium via a
  real `new Worker(...)`**, which is the shape the app deploys in. The browser
  figures are the ones the design uses; the Node figures are reported because
  they cross-check the browser ones and they cover more of the matrix.

### 1.2 Browser (Chromium, real Worker) — the deployment shape

### 1.4 What these numbers mean

1. **The browser Worker is ~31 % slower than Node** at the same settings
   (12,216 vs 9,328 ms at depth 14 / MultiPV 1). Any budget reasoned from a
   Node figure is optimistic by that much. The design uses §1.2.

2. **MultiPV is the expensive axis, not depth.** At depth 14, going from
   MultiPV 1 to 2 costs **2.6×** in the browser (12.2 s → 31.8 s) and to 3
   costs **5.5×** in Node. Going from depth 14 to 16 at MultiPV 2 costs 2.8×.
   A whole-game pass therefore has exactly one affordable configuration.

3. **`Hash 32` buys nothing at review depth** — it was marginally *slower*
   (27,797 vs 26,800 ms). The engine's existing `Hash 16`
   (`src/engine/EngineClient.ts`, set on `uciok`) stays. No engine option change
   is needed for review.

4. **The reference phone factor is an estimate, and the design does not depend
   on it.** No Galaxy A51 was available to this session, so the multiplier
   between the M1 browser figure and PRD §1.3's reference device is *not*
   measured here. Two independent anchors bracket it:
   - PRD F-RV-1 itself states "roughly half a second per position on the
     reference phone". Against the measured 151 ms at depth 14 / MultiPV 1,
     that implies a factor of **≈3.3×**.
   - Published single-thread WASM Stockfish throughput on Cortex-A73-class
     silicon is roughly 60–100 knps against the measured 347 knps, implying
     **3.5–6×**.

   Projected wall-clock for 81 positions at depth 14 / MultiPV 1:

   | factor | 3.3× (PRD's own) | 4× | 5× | 6× |
   |---|---|---|---|---|
   | total | 40 s | 49 s | 61 s | 73 s |

   So **depth 14 at MultiPV 1 sits exactly on the 60-second line** and anything
   richer is impossible. The plan carries a calibration task (Task 30) that
   records the real factor on a physical device, and the runtime design (§4.2)
   is self-tuning so that a wrong estimate degrades depth rather than breaking
   the budget.

### 1.5 The three design consequences

- **C1. The whole-game pass runs at MultiPV 1.** One evaluation per position.
  The evaluation of the move actually played is the *next* position's evaluation,
  negated — so 81 positions cover all 79 moves with 81 searches, not 158.
  (This is how Lichess does it; it makes the played move's evaluation one ply
  deeper than the best move's, which is noted in §9.4 as an accepted asymmetry.)
- **C2. Anything needing MultiPV ≥ 2 is confined to the ≤ 5 key moments**, in a
  second pass that runs **after** the summary is on screen and is therefore
  outside the 60-second budget. F-RV-1 already asks for this ("Key moments are
  then re-analysed at a higher depth"). Appendix C's **Great** ("the only move")
  and **Brilliant** ("a sound sacrifice… that is best or excellent") both need
  MultiPV ≥ 2 and are therefore **key-moment-only labels**.
- **C3. Depth is chosen at runtime from a measured rate**, not hard-coded.

## 3. The shape of the feature

Three screens, matching Wireframes-v1.1 screens 14, 15 and 16 and Concept-Note
§7's "board at the top, coach beneath it, one primary action at the bottom".

1. **Analysing** — progress bar, position N of M, cancel. Replaced in place by
   the summary.
2. **Summary** (screen 14) — accuracy for both sides, the opening name and the
   move the game left book, counts by label, the phase the game turned, then
   the key-moment list. Primary action: "Start with the first moment".
3. **Key moment** (screen 15) — the board before the learner's move, the coach
   asking for a better move, retry before reveal, "Show me", then the
   explanation and a link to the lesson. Primary action: "Next moment".
4. **Fix it** (screen 16) — three to five positions drawn from this game's
   error log, played through the existing `LessonPlayer`. Primary action:
   "Done" → back to the path, and the review is banked.

Route: `/play/review/:gameId`, added to the **modal block** of
`src/app/routes.tsx` (above the `*` route), beside `/play/game`, wrapped in
`ModalTask` — it is a single focused task with one way out, which is exactly
the invariant `src/app/ModalTask.tsx` documents.

## 4. The analysis service

### 4.1 Input: where a finished game comes from

This is the first thing the build has to solve, and it is not obvious from the
PRD.

`src/play/useGame.ts` writes exactly one record when a game ends:

```ts
await append({ type: 'game_finished', gameId, result, moves, hints, takebacks, crowns, pgn });
```

where `pgn` is **`state.sans.join(' ')`** — space-separated SAN, no headers, no
result token, no FENs. The `games` table declared in `src/data/db.ts` is
**never written to** by any code path. `GameState.history` (every FEN) exists
only in memory and dies with the route.

Two consequences:

- The learner's colour is **not** in `game_finished`. It is in `game_started`
  (`{ type: 'game_started', gameId, persona, color, timeControl, coach }`). The
  review must **join the two events on `gameId`**. A game whose `game_started`
  is missing (possible for a pre-existing device that predates this feature only
  if events were pruned — they are not) is unreviewable and says so.
- Positions are reconstructed by replaying the SAN list from `START_FEN` with
  `src/rules/applyMove`. This is sound because the app has no Chess960 and no
  set-position play. It is stated as an invariant in the code.

The service therefore takes a **`ReviewSource`**, not an event:

```ts
export interface ReviewSource {
  gameId: string;
  learner: Color;
  persona: string;
  sans: string[];
  result: 'win' | 'loss' | 'draw';
  timeControl: TimeControl;
  startedAt: string;
}
```

Import (F-RV-9, out of scope) would later build the same object from a PGN, and
the analysis path would not change. That is the seam.

### 4.2 The adaptive depth ladder (F-RV-1)

```
BUDGET_MS      = 60_000   // F-RV-1 "under 60 seconds"
WALL_MS        = 90_000   // F-RV-1 "if analysis exceeds 90 seconds"
CALIBRATE_N    = 6        // positions analysed before the ladder is chosen
LADDER         = [14, 12, 10]
```

1. Analyse the first `CALIBRATE_N` positions at depth 14, MultiPV 1, timing
   each. (Measured: 151 ms/position on an M1 browser, so calibration costs
   ~0.9 s there and ~4.5 s at a 5× factor — within budget on any device that
   could have finished at all.)
2. Project `total = mean × positionCount`. If `total ≤ BUDGET_MS`, stay at 14.
   Otherwise step down the ladder using the **measured ratios** from §1.3:
   depth 12 costs **0.63×** depth 14, depth 10 costs **0.19×** depth 14 (both at
   MultiPV 2; the plan re-measures at MultiPV 1 in Task 12 rather than assuming
   the ratio transfers — see §9.5).
3. Record the chosen depth on the review object and **show it**: the summary
   carries "Analysed at depth N" so a shallower review is never silently passed
   off as a full one.
4. A hard timer at `WALL_MS` stops the pass, marks the review `partial`, renders
   what exists, and continues the remaining positions in the background via the
   same `EngineClient` queue. `partial` is visible on the summary
   ("Still analysing the last N moves"), and the review cannot be **banked**
   (§8) until it completes.

Why a ladder and not a fixed depth: §1.4.4 shows the phone factor is unmeasured
here. A fixed depth 14 is correct at 3.3× and 40 s over budget at 6×. A ladder
keyed on a rate measured *on the device in the moment* is correct at every
factor, and its worst case is a shallower review, which is a product
degradation rather than a broken promise. This is the single most important
structural decision in the document.

### 4.3 Engine discipline

- **One `EngineClient`, the shared one** — `getEngine()` from `src/engine`. It
  already serialises work FIFO, pauses during drags (`pause()`/`resume()`), and
  terminates the worker after 60 s idle. The review must not construct a second
  client: two clients means two WASM instances and two heaps on a phone.
- The review submits **one `analyse()` per position and awaits it** before
  submitting the next. It must not enqueue 81 jobs at once, because the queue
  has no cancel and `dispose()` rejects everything including the board's own
  jobs. Cancelling the review = stop submitting.
- `EngineUnavailable` from any position aborts the pass, surfaces
  `F-ER`-style copy ("The engine could not start. Try again."), and leaves the
  game reviewable later. Positions already analysed are kept.
- `Analysis.depth` on the result is the **requested** depth, not the reported
  one (`EngineClient.ts` sets it from `job.depth`). The review therefore records
  its own requested depth and does not read it back as evidence.

### 4.4 Output

```ts
export interface ReviewedMove {
  ply: number;              // 0-based index into sans
  san: string;
  uci: string;
  fenBefore: string;
  fenAfter: string;
  mover: Color;
  best: { uci: string; san: string };
  winBefore: number;        // win% for the mover at fenBefore, i.e. with best play
  winAfterPlayed: number;   // win% for the mover after the move played
  drop: number;             // max(0, winBefore - winAfterPlayed)
  accuracy: number;         // moveAccuracy(drop)
  label: MoveLabel;
  book: boolean;
}

export interface Review {
  gameId: string;
  learner: Color;
  depth: number;
  partial: boolean;
  moves: ReviewedMove[];
  accuracy: { w: number; b: number };
  counts: Record<MoveLabel, number>;
  opening: { name: string; leftBookAtPly: number | null } | null;
  turningPhase: 'opening' | 'middlegame' | 'endgame' | null;
  keyMoments: KeyMoment[];
  errors: ErrorEntry[];
}
```

## 5. Labels (F-RV-2, §10.6, Appendix C)

### 5.1 The formulas are already shipped

`src/engine/winPercent.ts` implements PRD §10.6 exactly and is unit-tested:

```ts
export function toWinPercent(cp: number): number            // 50 + 50*(2/(1+e^(-0.00368208*c)) - 1), clamped to ±1000 cp
export function scoreToWinPercent(s: Score): number         // mate>0 → 100, mate<0 → 0
export function moveAccuracy(winDrop: number): number       // 103.1668*e^(-0.04354*drop) - 3.1669, clamped 0..100
```

**Constraint: the review imports these. It does not restate the formulas.**
Any second implementation is a plan defect. The plan's Task 8 includes a test
that asserts the label module's win-percent values equal `toWinPercent`'s for a
sweep of centipawn inputs, so a copy cannot be introduced silently later.

### 5.2 Appendix C, reproduced as the implementation table

Drop is in win per cent. Bands are the PRD's four sections.

| Label | Base | S1 & S2 | S3 | S4 |
|---|---|---|---|---|
| Best | 0 | 0 | 0 | 0 |
| Excellent | < 2 | < 3 | < 2.5 | < 2 |
| Good | 2–5 | 3–8 | 2.5–6 | 2–5 |
| Inaccuracy | 5–10 | 8–15 | 6–12 | 5–10 |
| Mistake | 10–20 | 15–25 | 12–22 | 10–20 |
| Blunder | ≥ 20 | ≥ 25 | ≥ 22 | ≥ 20 |

Overrides applied after the numeric band, in this order:

1. **Book** — the position after the move is in the bundled opening book and the
   move is within the first ten moves (20 plies). Book wins over every numeric
   label. (§9.2 records the deviation from Appendix C's wording.)
2. **Miss** — "a mistake or worse played when the opponent's previous move was a
   mistake or worse". Replaces Mistake/Blunder, does not replace Inaccuracy or
   better.
3. **Great** — key-moment second pass only: the played move is Best and the
   second-best line's drop is ≥ the band's Mistake floor, i.e. it was the only
   move that avoided a mistake.
4. **Brilliant** — key-moment second pass only: Great's MultiPV data plus a
   material sacrifice that is not immediately regained, the move is Best or
   Excellent, and `winBefore` was **not** already ≥ 80 (the operational reading
   of "not already clearly winning"; recorded in §9.3 as a chosen constant).

Mate handling, per §10.6 "Mate-related judgements follow the Lichess rules":
- Allowing a forced mate (`winBefore` finite, `winAfterPlayed` = 0 by mate)
  is a **Blunder**, unless `winBefore < 20` — already lost by a wide margin — in
  which case the numeric band applies.
- Delaying a mate the mover already had (mate in n → mate in n+k, both for the
  mover) carries **no label penalty**: it is Best if it is still mating.
- `scoreToWinPercent` already collapses mate to 100/0, so the drop arithmetic
  needs no special case beyond the two rules above.

### 5.3 Band selection

The learner's band comes from their furthest section on the path. Only
Section 1 exists in `src/path/curriculum.ts` today, so **every live learner is
in the S1 & S2 column**. The other three columns are implemented and unit-tested
but unreachable in the shipped app. This is stated so that a later reviewer does
not read the untested-in-production columns as dead code and delete them.

### 5.4 Presentation — no new colour tokens

Eight labels could have taken eight new colour tokens in
`src/app/theme.css`. They do not, for two reasons: a token layer is a shared
vocabulary and would force every other chunk to wait on it, and
`tests/audit-platform/controls.spec.ts` and `tests/audit/audit-helpers.ts`
sweep every token for contrast and shadow identity, so eight new hues is eight
new sweep obligations for no product gain.

Instead each label is carried by **three channels**: its **name in text**
(always present, never truncated), a **distinct glyph**, and one of the three
**existing** semantic tokens.

| Label | Glyph | Token |
|---|---|---|
| Brilliant | `!!` | `--mark-good` |
| Great | `!` | `--mark-good` |
| Best | `★` | `--mark-good` |
| Excellent | `◆` | `--mark-good` |
| Good | `✓` | `--content` |
| Book | `▤` | `--content-dim` |
| Inaccuracy | `?!` | `--mark-review` |
| Mistake | `?` | `--mark-review` |
| Miss | `⊘` | `--danger` |
| Blunder | `??` | `--danger` |

Colour is never the only channel, satisfying the accessibility constraint and
WCAG 1.4.1. Glyphs are `aria-hidden`; the name is the accessible text.

## 6. The fix-it drill (F-RV-7) — the decision, argued

**Decision: build a minimal version, in scope, this plan.**

### 6.1 The case for dropping it

F-RV-7 as written describes "a three-to-five-puzzle drill built from the error
log" and PRD §6.1 step 4 says "similar positions… scheduled for today and again
at growing intervals". Both sentences presuppose two things the repo does not
have: a puzzle ladder to draw *similar* positions from, and a spaced-repetition
scheduler to re-queue them. PRD §14 puts "fix-it drills" in Phase 2 Beta
alongside the puzzle work. On the letter of the release plan, deferring is the
defensible reading.

### 6.2 The case for building it

1. **The loop is the product.** §6.1 names one loop, learn-apply-**review**-fix.
   Shipping review without fix ships three quarters of the mechanism the PRD's
   strongest evidence is about, and leaves the error log — the thing review
   exists to produce — with no consumer in the app. An unconsumed error log is
   indistinguishable from a broken one for as long as nothing reads it.
2. **F-RV-7 owns the North Star clause.** "Completing the drill completes the
   plan's review item." The DAL definition in §2.2 counts "a game review". If
   the drill is the completion signal and the drill does not exist, §8's banking
   rule has to be invented anyway — so the requirement is not avoided by
   deferring it, only made implicit.
3. **The infrastructure cost is close to zero, and it is already proven.**
   `LessonPlayer` takes an ordinary `Lesson` object as a prop; nothing requires
   that object to come from a file. `loader.ts` reads authored packs, but the
   player does not depend on the loader. The `find_the_move` challenge type is
   `{ id, fen, prompt, concept, answer: { moves: string[] }, hints?, reason? }`
   — every field of which the error log already holds. So a drill is a pure
   function `ErrorEntry[] → Lesson`, rendered by a component that ships and is
   covered by 343 unit and 221 Playwright tests. No new player, no new
   challenge type, no new content pipeline, no scheduler.
4. **The honest scope is narrower than F-RV-7 and should be labelled as such.**
   The drill replays **the learner's own mistakes from this game**, not
   "similar positions" from a ladder. That is retrieval practice on the exact
   position the learner just got wrong, which is the cheaper and better-evidenced
   half of the idea. The spaced part (§6.1 "again at growing intervals") is
   genuinely out of reach and is deferred with its destination.

### 6.3 What ships, precisely

- Input: the `ErrorEntry[]` from this review, mistakes and blunders only,
  ranked by drop, capped at 5, floor of 3. **If fewer than 3, no drill is
  offered** and the review banks on the last key moment instead; a two-question
  drill would be worse than none and the copy would have to lie about "three to
  five".
- Each entry becomes a `find_the_move` challenge whose `fen` is `fenBefore`,
  whose `answer.moves` is `[best.uci, best.san]`, whose `concept` is the motif
  tag, and whose `prompt` is the templated line from the coach bank.
- Rendered by `LessonPlayer` with `hintsAllowed={false}` (the answer was just
  revealed at the key moment), `showXp={false}` (XP is awarded by the review's
  own event, not by the player), `exitLabel="Exit review"`,
  `closeHeading="Review done"`, `closeAction="Back to the path"`.
- `onOutcome` fires once; that is the banking point (§8).

### 6.4 What is deferred and where

"Similar positions from the puzzle ladder" and "scheduled again at growing
intervals" → **Phase 2 Beta puzzle plan**. The `ErrorEntry` shape specified in
§7.3 carries `theme`, `phase`, `clockMs`, `lessonId` and `typical` precisely so
that the scheduler can be added over it without a migration.

## 7. The other pieces

### 7.1 Key moments (F-RV-4)

Selection, in order:

1. Compute `swing = drop` for every move **made by the learner**. (The
   opponent's blunders are not the learner's moments; the opponent is a bot.)
2. Take the three required kinds where each exists:
   - **the mistake that decided the game** — the learner's largest drop that
     took `winAfterPlayed` below 50 when `winBefore` was above it;
   - **a chance the learner missed** — the largest drop labelled `Miss`, else
     the largest drop where `winBefore ≥ 80` and `winAfterPlayed < 80`;
   - **a good move the learner found** — the move with the largest
     `winAfterPlayed − winBefore` that is labelled Best or Excellent and is not
     a book move.
3. Fill to five by descending swing, skipping plies already chosen and skipping
   book moves.
4. Floor of three. If fewer than three qualify (a clean short game), ship what
   there is; the summary says "2 moments in this game" rather than padding.

Each selected moment gets the §4.2 second pass (**depth 16, MultiPV 2**) queued
in the background as soon as the summary renders. Measured cost: 913 ms/position
in Node at those settings (§1.3), ≈1.2 s in the browser, so 5 moments is ≈6 s on
an M1 and ≈30 s at a 5× factor — entirely overlapped with the learner reading
the summary and working the first moment. **If a moment's second pass has not
landed when the learner reaches it, the moment renders from the first-pass data
and the Great/Brilliant line is omitted.** It is never guessed: F-CO-4.

### 7.2 Explanations (F-RV-5, F-CO-4)

`src/coach/CoachService.line(event, facts)` **throws** when a template needs a
fact the caller did not supply. That is the designed honesty mechanism and the
review uses it unchanged: new review templates are added to
`content/coach/templates.json`, and the review builds its facts object from
**only** these verified sources:

| Fact | Verified by |
|---|---|
| `best`, `pv` | `EngineClient.analyse` |
| `winBefore`, `winAfterPlayed`, `drop` | `winPercent.ts` over engine scores |
| `hanging`, `capture`, `mateInOne`, `threats` | `src/tagger/tagger.ts` |
| `piece`, `square`, `san` | `src/rules` |
| `lessonId`, `lessonTitle` | the concept → lesson map (§7.4) |

Nothing else may enter a template. A missing fact is a thrown error caught at
the moment boundary, which renders the moment **without** an explanation rather
than with an invented one. The plan's Task 20 asserts that path explicitly, with
its own error handler, because a test whose subject is a thrown error needs the
error path to be the handled path.

### 7.3 Error log (F-RV-6)

```ts
export interface ErrorEntry {
  gameId: string;
  ply: number;
  fenBefore: string;
  playedSan: string;
  bestSan: string;
  bestUci: string;
  label: 'Mistake' | 'Blunder' | 'Miss';
  theme: string;             // motif tag from the tagger, or 'unclassified'
  phase: 'opening' | 'middlegame' | 'endgame';
  clockMs: number | null;    // null for untimed games — the only clock is 10+0
  lessonId: string | null;
  typical: boolean;
  createdAt: string;
}
```

- **theme** comes from `facts(fenBefore)` plus the played/best move: hanging
  piece, winning capture missed, mate in one missed, threat ignored. The full
  motif set in PRD §10.3 (fork, pin, skewer, discovered attack, back-rank,
  deflection…) is **not** in `src/tagger/tagger.ts` today, so unmatched errors
  are tagged `'unclassified'` and are still logged. Extending the tagger to
  §10.3's full list, with the 2,000-puzzle 95 % agreement test, is its own plan.
- **phase**: opening = ply < 20 or still in book; endgame = both sides have
  ≤ 13 points of non-king material by `PIECE_VALUE`; otherwise middlegame.
- **clockMs**: from the game's time control. `GameState.clockMs` is not
  persisted, so for `10+0` games the field is `null` in this release and the
  shape is kept for when it is. Stated, not silently dropped.
- **typical**: F-RV-6 says "from the puzzle ladder in the first release". There
  is no puzzle ladder. Operational substitute, stated: `typical` is true when
  the theme is one of the four the Section 1 curriculum teaches
  (hanging piece, missed capture, missed mate in one, ignored threat) — i.e.
  "typical at the learner's level" means "the curriculum at this level teaches
  exactly this". Recorded in §9.6.

Persisted in a new Dexie `reviews` table (`db.version(3)`), keyed on `gameId`,
holding the whole `Review` object. The event log stays the source of truth for
*progress*; the review table is a cache of expensive derived data, rebuildable
from the events at any time.

### 7.4 Opening book (F-RV-3) — decision and the number

**Decision: include it. 39.6 KiB over the wire — built and measured, not estimated.**

Measured, not estimated. Source: `lichess-org/chess-openings` (CC0, PRD §9.1
and Appendix D), fetched at build time: 3,810 named lines across `a.tsv`–`e.tsv`,
388 KiB of raw TSV, median line depth 9 plies, max 36.

Two encodings were built and measured:

| encoding | cap | entries | raw | gzip | **brotli** |
|---|---|---|---|---|---|
| 48-bit position hashes + name blob | 20 plies | 7,592 | 208.5 KiB | 77.8 KiB | 70.7 KiB |
| **sorted UCI move-paths + name blob (the shipped file)** | **20 plies** | **3,704** | **299.3 KiB** | 47.4 KiB | **39.6 KiB** |
| sorted UCI move-paths | 16 plies | 3,424 | 273.2 KiB | 44.4 KiB | 37.1 KiB |
| sorted UCI move-paths | 12 plies | 2,833 | 211.4 KiB | 36.6 KiB | 30.3 KiB |
| sorted UCI move-paths | no cap | 3,810 | 321.9 KiB | 50.6 KiB | 42.4 KiB |

The hash form is bigger over the wire because 48-bit hashes are incompressible
by construction; the move-path form is sorted text with heavy shared prefixes
and compresses 7.5×. The move-path form also needs no hashing, carries no
collision risk, and matches the access pattern exactly — the review already
walks the game from move 1, so it walks the trie in step.

**Cap: 20 plies**, because Appendix C's Book rule is "within the first ten
moves" and ten moves is twenty plies. The no-cap form saves nothing.

**Why this does not touch the 300 KB budget.** PRD §2.2 and §11 state the budget
as "**App shell** under 300 KB of **JavaScript** compressed", and §11 adds "The
engine is never on the critical path of first load." The book is neither app
shell nor JavaScript: it ships as `public/data/openings.txt`, a static asset
fetched **on first review only**, cached by the service worker's runtime cache
alongside the engine. Built: 3,704 lines, 3,088 distinct names, 106 of the
3,810 source lines dropped for exceeding 20 plies, 0 failing to replay legally.
The 235 KiB shell figure is unchanged — the plan's Task 5
asserts that by measuring the built bundle before and after. (The premise that
the 300 KB budget applies to bundled data is not in the PRD; §9.1 records this.)

Lookup: walk the game's UCI moves through the sorted path list (binary search
per prefix). The **name** is the deepest prefix with a name; **left book at**
is the first ply whose path prefix is absent. Both are what F-RV-3 asks for.

### 7.5 Accuracy and the turning phase (F-RV-3)

- Per-side accuracy = the arithmetic mean of `moveAccuracy(drop)` over that
  side's non-book moves, to one decimal. Book moves are excluded because a book
  move's drop is meaningless (the engine's "best" in a book position is a
  preference, not a requirement). If a side has no non-book moves, accuracy is
  `null` and renders as "—", not as 100.
- Turning phase = the phase (§7.3) containing the learner's single largest drop
  that crossed `win% = 50`. If no move crossed 50, `null`, rendering as "the
  game never really turned".

## 8. Making a review count (North Star)

A new event:

```ts
| { type: 'game_reviewed'; gameId: string; accuracy: number; blunders: number; mistakes: number; drillCompleted: boolean; partial: false }
```

- Appended **exactly once per game**, guarded by a `useRef` in the same shape as
  `useGame.ts`'s `finished` guard, **and** by the presence of a prior
  `game_reviewed` for that `gameId` in the projection, so a second visit to the
  review route cannot double-count.
- **The append happens before the success screen renders its heading**, not on
  the exit control. A screen that states a fact must have banked the state that
  makes it true; a commit attached to one exit turns every other exit — back
  gesture, tab switch, app kill — into silent loss, and the announcement is
  exactly what stops anyone looking.
- `partial` reviews never append. `partial: false` is in the payload as a
  literal so the type makes the rule unstateable otherwise.
- The banking point is: the fix-it drill's `onOutcome`, or — when fewer than
  three errors mean no drill (§6.3) — the last key moment's "Finish" action.
- `reduceProgress` gains `reviews: number` and `gamesReviewed: Record<string, true>`.
  The second is what makes the double-count guard a projection question rather
  than a component question.

## 9. Where the PRD cannot be implemented as written

Each item states what the PRD says, why it cannot be done literally, and what
ships instead. None of these were decided silently.

### 9.1 The "300 KB budget" does not cover bundled data

The brief for this design assumed a 300 KB bundle budget "currently at 235 KiB"
against which the opening book had to fit. **There is no such budget in the
PRD.** §2.2 and §11 both scope 300 KB to "app shell… JavaScript compressed".
Treating a lazily-fetched static data file as competing with the app shell's JS
budget would be a self-imposed constraint with no source. The book is therefore
specified as a runtime-cached static asset (§7.4) and the shell budget is
asserted unchanged by measurement rather than argued.

### 9.2 Appendix C's Book rule needs frequency data the cited source has not got

Appendix C defines Book as a move "that appears in at least **5 per cent of
games** from that position in the bundled opening book (built from the Lichess
database across all bands)". PRD §9.1 sources the bundled book from
`lichess-org/chess-openings`, which is a list of **named lines** and contains
**no game counts at all**. The 5 % rule is computable only from the Lichess
opening **explorer**, which §9.1 lists separately as an **online** API — and
F-RV-10 requires review to work offline.

**Ships instead:** Book = "the position after the move is a node of the bundled
named-openings book, within the first 20 plies". This is stricter in one
direction (a popular sideline with no ECO name is not Book) and looser in
another (a named but rare line is Book). It is offline, CC0, and 39.6 KiB over the wire.
**Destination for the real rule:** a build-time frequency extract from the
Lichess database dumps, sized and specified in its own plan — it is a different
data source with a different licence question, not a tuning constant.

### 9.3 "Not already clearly winning" has no number

Appendix C's Brilliant rule says "from a position that was not already clearly
winning". No threshold is given anywhere in the PRD. **Ships:** `winBefore < 80`,
chosen because inverting the shipped curve puts win% 80 at **+376 centipawns**
(computed, not recalled: `ln(80/20) / 0.00368208 = 376`), i.e. very close to a
whole extra rook — a defensible reading of "clearly winning". It is a named
constant, `BRILLIANT_MAX_WIN_BEFORE`, with a comment pointing at this section,
so beta tuning is a one-line change rather than an archaeology exercise.

### 9.4 The played move is evaluated one ply deeper than the best move

Taking the played move's value from the next position's search (§1.5 C1) means
it is searched to depth *d* from a node one ply further on. The alternative —
searching the played move separately — doubles the pass and is impossible
inside the budget (§1.4.2). Lichess's own analysis has the same asymmetry. The
effect is a small systematic bias toward judging the played move slightly
harshly in sharp positions. **Accepted and documented in the code**, not hidden.

### 9.5 The depth-ratio constants are measured at MultiPV 2, not 1

§1.3's depth 10 / 12 / 14 rows are all MultiPV 2, because that was the matrix
that completed. The ladder in §4.2 uses ratios derived from them at MultiPV 1.
The plan does **not** assume the ratio transfers: Task 12 re-measures depths 10,
12 and 14 at MultiPV 1 over the same 81 positions and writes the measured
constants into the code, with the test asserting monotonicity rather than the
literal numbers.

### 9.6 "Typical at the learner's level" has no first-release source

F-RV-6 says typicality comes "from the puzzle ladder in the first release". The
puzzle ladder does not exist (`src/screens/PuzzlesScreen.tsx` is a placeholder,
and PRD §14 puts puzzles in Phase 1 Alpha). **Ships:** the curriculum-taught-
theme substitute in §7.3, flagged in the UI as "Section 1 teaches this" rather
than as a population claim, because the honest statement is about the
curriculum and not about other learners.

### 9.7 F-RV-1's "0.5 s per position" is an estimate, and it is about the right size

Not a defect — worth recording because it is the only performance figure in the
PRD and this is the first time it has been checked. Against §1.2's measured
151 ms on an M1 browser it implies a 3.3× device factor, which is at the
optimistic end of the 3.5–6× bracket in §1.4.4 but not unreasonable. The
consequence is that F-RV-1's 60-second promise is **achievable only at
MultiPV 1**, which F-RV-1 does not say and Appendix C's Great and Brilliant
rules implicitly contradict. §1.5 C2 resolves it.

## 10. Accessibility

Binding on every screen in §3.

- The key-moment board is the **shared `Board`** (`src/board/Board.tsx`) in
  `mode="play"` with its existing keyboard cursor, single live region and one
  tab stop. No second board, no second live region. The review's own status
  messages go through the board's `announce` prop or a single `role="status"`
  on the screen — never both at once.
- Every label is name + glyph + token (§5.4). Colour is never the only channel.
- All controls ≥ 44 px, per `tests/audit-platform/controls.spec.ts`.
- The layout must survive a 32 px root (largest text size) without horizontal
  scroll — the label counts table is the risk, and it is specified as a
  wrapping list rather than a fixed grid. Measured by
  `tests/audit-platform/reflow.spec.ts`'s existing sweep, extended to the new
  route.
- The progress bar is `role="progressbar"` with `aria-valuenow`/`max` and a
  visible text equivalent ("Move 24 of 79"), because a bar alone is not a
  readable quantity.
- Light theme only. No `prefers-color-scheme` branch is added.
